## What's happening

The GitHub tile on the home page shows my contribution count for the last year plus a small 7-day sparkline. There's no backend and no client-side GitHub API call — the widget just reads a JSON file, `public/data/github.json`, over HTTP at load time.

That file is written by the same daily sync that feeds the [LeetCode tile](/colophon/leetcode-sync): a GitHub Actions cron runs a small Node script, commits the result to the repo, and the next deploy picks it up.

## The data path

The tile reads the committed JSON — nothing more:

```ts
useEffect(() => {
  fetch(`${import.meta.env.BASE_URL}data/github.json`)
    .then((r) => (r.ok ? r.json() : null))
    .then(setData)
    .catch(() => setData(null))
}, [])
```

The shape is `{ username, fetchedAt, totalLastYear, days: { "YYYY-MM-DD": count } }`. `totalLastYear` renders as the "contributions" number; the last seven entries of `days` become the sparkline. If the fetch fails, the widget stays in its skeleton state and nothing else on the page is affected.

## The script

One GraphQL query against GitHub's `contributionsCollection.contributionCalendar` — the calendar you see on a profile page:

```js
const QUERY = `
  query ($login: String!) {
    user(login: $login) {
      contributionsCollection {
        contributionCalendar {
          totalContributions
          weeks {
            contributionDays {
              date
              contributionCount
            }
          }
        }
      }
    }
  }
`
```

The script keeps only active days (count > 0), keyed by ISO date — the page fills in the zeros — and writes `totalContributions` as `totalLastYear`. It needs a `GITHUB_TOKEN` in the environment; the token the Actions runner already provides works, since the contribution calendar is public data readable with any valid token.

## The cron

The GitHub and LeetCode fetches share one workflow — "Sync stats" — on a daily cron:

```yaml
on:
  schedule:
    - cron: '17 6 * * *' # daily ~06:17 UTC
  workflow_dispatch:
```

It runs both scripts, then commits whatever changed under `public/data/`:

```yaml
- name: Commit if changed
  run: |
    if [[ -n "$(git status --porcelain public/data/)" ]]; then
      git config user.name "github-actions[bot]"
      git config user.email "41898282+github-actions[bot]@users.noreply.github.com"
      git add public/data/leetcode.json public/data/github.json
      git commit -m "chore: refresh LeetCode + GitHub stats"
      git push
    fi
```

That push to `main` is all it takes — Cloudflare Pages auto-builds on the resulting commit, so there's no deploy workflow to dispatch.

## Why this shape

This used to be a client-side fetch to `api.github.com` with a `localStorage` cache — a "static site, no backend" pattern from when the site lived on GitHub Pages. It worked, but every visitor's browser hit the API, and the contribution calendar isn't available from the unauthenticated REST endpoint anyway.

Moving to a committed JSON means the build never depends on GitHub being reachable. If a sync run breaks, the page keeps showing the last successful snapshot until the next cron tick fixes it — and both the home tile and the Stats page read the same file with one fetch. Treating the GitHub tile exactly like the LeetCode one keeps the rendering code identical and makes the source of truth a single JSON file in the repo.
